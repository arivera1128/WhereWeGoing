Accepted direction

Product north star

Help someone answer “Where should we eat tonight?” confidently in about 30 seconds.

Present one clear recommendation, a few useful alternatives, relevant deal context, and an honest explanation grounded in the user’s situation.

Open app→Request a pick→See winner→Understand why→Choose

MVP boundaries

  • Food and restaurants
  • Lightweight household and preference profile
  • Nearby and currently relevant candidates
  • One winner plus a small set of alternatives
  • Explainable recommendation and trustworthy deal context

Outside the confirmed MVP

  • Merchant platform and paid placement
  • Deep rewards integrations
  • Predictive personalization
  • Other deal categories
  • Nationwide launch and iOS implementation

Observed in repository

Current application

Working prototype

  • Android app written in Kotlin with Jetpack Compose
  • Warm chick-themed visual design and drawer navigation
  • Home, Tonight’s picks, Food profile, Profile, deal details, and Removed places
  • First-time Food Profile preview and established-user rating management
  • Local profile, ratings, feedback, and removal storage using SharedPreferences
  • Curated prototype restaurant and deal constants

Current limitations

  • Most UI and state live in one large MainActivity.kt file
  • No backend, shared API, database, authentication, or environment separation
  • Recommendation logic only uses a limited subset of collected preferences
  • Restaurant, location, deal, and applicability concepts are not yet separated
  • Deals remain embedded in app code
  • No agreed event contracts or real-data sandbox
Current interpretation: the prototype validates interaction ideas. It is not yet the architecture described by the forward-looking documents, and it should be evolved rather than discarded.

Proposed sequence

Roadmap phases

Phases express dependency order, not calendar promises. A later phase may be discussed early, but implementation should respect unresolved gates.

Phase 1
Now

Baseline and modular prototype

Confirm the MVP journey, inventory existing behavior, split the Android code into understandable UI, domain, and data responsibilities, and preserve the working experience.

Phase 2
Proposed

Recommendation engine version 1

Define an explainable rules-based score using location, timing, eligibility, explicit preferences, exclusions, household context, savings, and deal confidence.

Phase 3
Proposed

Logical model and access patterns

Pressure-test Restaurant, Location, Deal, DealLocation, evidence, profiles, preferences, and events. Define the actual reads and writes before selecting physical storage.

Phase 4
Decision gate

Backend and physical data design

Compare backend and database options against access patterns, security, geography, cost, environment isolation, and owner learning needs. Define an API boundary.

Phase 5
Proposed

Real-data sandbox and deal trust

Load real Elk Grove restaurant/location records, clearly labeled synthetic deals, and a smaller verified deal set. Exercise evidence, publication, applicability, and retirement.

Phase 6
Later

Feedback, learning, and operations

Implement the accepted subset of intent, visit, deal confirmation, and preference feedback. Add only the internal controls required to maintain trustworthy data.

Phase 7
Later

MVP validation and release readiness

Test family and solo contexts, exclusions, expired and uncertain deals, no-result cases, environment isolation, and the 30-second decision aspiration.

Session 2 · Modularize the Android prototype
GoalReduce the growing MainActivity without changing product behavior.
PrerequisiteInventory existing screens and state.
OutputSeparate UI, domain, and data files with a clean state boundary.

Suggested scope

  • One file or package per screen
  • Reusable UI components
  • Plain Kotlin domain models
  • Local repository interfaces
  • Top-level app/navigation state separated from screen rendering

Done when

  • Existing prototype builds
  • Primary flows behave the same
  • Recommendation logic can be tested without Compose
  • Storage can later be replaced behind interfaces
Session 3 · Design recommendation scoring version 1
GoalDefine a simple, explainable selection method.
PrerequisiteConfirmed MVP inputs and basic domain boundary.
OutputScoring table, filters, tie-breakers, and explanation rules.

Questions

  • Which conditions exclude a candidate?
  • Which inputs add or subtract score?
  • How do explicit ratings affect inferred category preferences?
  • When is a deal too uncertain to recommend?
  • How is “no strong deal” handled?

Done when

  • Hard filters and soft preferences are distinct
  • Every score component can produce a user-facing reason
  • Family and solo examples produce sensible differences
  • No unsupported savings or confidence is invented
Session 4 · Validate the logical data model
GoalTest business concepts before thinking in tables or collections.
PrerequisiteReview the existing Data Model and Deal Lifecycle.
OutputAccepted relationships and a short unresolved-rules list.

Scenarios

  • Independent restaurant with one location
  • Chain deal with participating and unknown locations
  • Recurring and overnight offer
  • Expired offer and conflicting evidence
  • User exclusion versus mild preference
  • Intent without visit and failed deal without restaurant dislike

Done when

  • Restaurant, Location, Deal, and applicability relationships hold
  • Unknown is not treated as confirmed or excluded
  • Evidence survives rejection, merge, correction, and retirement
  • Remaining product rules are explicit
Session 5 · Define access patterns and expected scale
GoalDescribe what each application area must read and write.
PrerequisiteValidated logical model and recommendation inputs.
OutputQuery/write catalogue and volume assumptions.

Key access patterns

  • Find supported locations within a radius
  • Find currently valid deals and resolve location applicability
  • Load profile and explicit preferences
  • Write recommendation and selected feedback events
  • Review evidence and lifecycle queues

Done when

  • Every MVP screen has known data needs
  • Geographic, time, pagination, and authorization needs are listed
  • Read/write frequency assumptions are recorded
  • Physical design can be compared objectively
Session 6 · Select backend, database, and API boundary
GoalChoose technology based on known requirements.
PrerequisiteAccess patterns, scale, privacy, and environment needs.
OutputDecision record and reviewed physical design.

Compare

  • Firebase/Firestore
  • Relational database plus an API
  • Kotlin server versus TypeScript or another supported backend
  • Managed identity and anonymous-user migration choices

Done when

  • Choice, alternatives, costs, and tradeoffs are documented
  • Dev, QA/staging, and production isolation is designed
  • Authorization and backup/recovery responsibilities are identified
  • The Android app depends on an API/repository boundary rather than storage details
Session 7 · Design the real-data sandbox
GoalCreate safe, useful data for end-to-end testing.
PrerequisiteProvider/legal review and physical design.
OutputSeed plan, labels, provenance rules, and test cases.

Dataset layers

  • Real Elk Grove restaurant and location records
  • Clearly marked synthetic offers for edge cases
  • Smaller source-verified genuine deal set

Done when

  • Provider storage and caching terms are understood
  • Every deal has provenance and environment
  • Synthetic data cannot enter production
  • App data can change without changing Kotlin constants
Session 8 · Decide the MVP feedback loop
GoalSelect the smallest meaningful learning loop.
PrerequisiteCore recommendation journey is stable.
OutputAccepted events, screens, and meanings.

Keep distinct

  • Recommendation shown
  • Intent or “Let’s go”
  • Visit reported
  • Deal available and honored
  • Restaurant or recommendation preference

Done when

  • Missing feedback remains unknown
  • A failed deal does not become a restaurant dislike
  • Retries and duplicate events have a policy
  • Only approved MVP events are implemented
Session 9 · Validate the complete MVP journey
GoalEvaluate whether the product promise works end to end.
PrerequisiteConnected recommendation, data, and selected feedback flow.
OutputEvidence, limitations, and prioritized corrections.

Validation cases

  • Family and solo profiles
  • Strong match, weak match, and no result
  • Explicit restaurant exclusion
  • Expired, unknown, and conflicting deals
  • Eligibility differences
  • First-time and returning-user paths

Done when

  • Measurement definition for 30 seconds is agreed
  • Incorrect recommendations are traceable
  • Trust disclosures are accurate
  • Next changes are based on observed problems

Proposed

Why this comes first

The prototype already has several screens, while the new documentation introduces a larger product and data vision. A short MVP-definition session gives later architecture, scoring, and database work a stable target.

What we would decide

  1. The exact first-time and returning-user journey.
  2. The minimum information a winning recommendation must show.
  3. The MVP feedback actions.
  4. The no-result and uncertain-deal behavior.
  5. The evidence that tells us the prototype succeeded.

Expected artifact

A short accepted MVP specification, recorded in the product and decision documents, followed by a bounded modularization plan for the Android app.
